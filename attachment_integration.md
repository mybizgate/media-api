# MyBizGate — Attaching media-api files to business records

**File:** `media-api/attachment_integration.md` | **Updated:** 2026-10-30
**Applies to:** any MyBizGate backend (`client-api`, future `booking-api`, `registration-api`, …) and their Vue frontends.
**Source of truth:** this document describes what `media-api` does **today**, verified against `routes/api.php`,
`MediaController`, `ResolveTenant`, `UploadMediaRequest`, `ReplaceMediaRequest`, `AssignMediaRequest`, `MediaResource`,
`FilesystemMediaRepository`, `config/media.php` and `config/cors.php`. `README.md` stays the full API reference.
`client-api` is the reference consumer (§5).

## 1. What media-api is (and is not)

```
Vue / mobile UI ──► client-api   (products, services, users …  + media_attachments table)
              └──► media-api    (file bytes + metadata.json, no database)
```

- `media-api` has **no database** of any kind (no MySQL, no sqlite). Each file lives in its own directory with a
  `metadata.json` beside it, and that directory layout is the index:
  `tenants/{tenant}/images/{module}/YYYY/MM/{media-id}/image.webp | thumb.webp | metadata.json` and
  `tenants/{tenant}/files/{module}/YYYY/MM/{media-id}/file.{ext} | metadata.json`.
  Production root: `/home/mybizgat/data/media-api/uploads`. Consumers never see or depend on these paths; the API
  only ever returns URLs.
- Every item carries `tenant`, `module` and an optional `entity_id`. That is the built-in link to a business
  record (§4, option A). media-api never reads or writes a consumer's `media_attachments` table (§4, option B); the
  only thing the two sides share is the media id, carried over HTTP.
- **Tenant identification is the `X-Client-Code` header** (`^[a-z0-9-]{2,50}$`, e.g. `lzhub`). There is no caller
  authentication and none is planned: attachments are public product/service photos, so the header only scopes
  writes and listings to a tenant. The tenant is never read from a request body.
- Media ids are **lowercase ULIDs** (`^[0-9a-z]{26}$`), generated by media-api. Anything else in `{id}` is a `404`.

## 2. Endpoints (base `https://media-api.mybizgate.com/api/v1`)

| Method | Path | Header | Returns |
|---|---|---|---|
| `GET` | `/health` | – | `status`, `service`, `version`, `environment`, `deployment`, `storage`, `gd`, `webp`, `avif`, `timestamp` |
| `GET` | `/ping` | – | `{"success":true,"data":{"pong":true,"time":"…"}}` (deployment smoke test) |
| `GET` | `/media?module=&entity_id=&media_type=&year=&month=&page=&per_page=` | required | JSON list + `meta` paging |
| `POST` | `/media` | required | `201` JSON of the new item |
| `GET` | `/media/{id}` | optional | **bytes**: images and PDF inline, other files as download |
| `GET` | `/media/{id}/thumbnail` | optional | **bytes**: WebP ≤ 400×400 (images only, `404` for documents) |
| `GET` | `/media/{id}/metadata` | optional | JSON of the item |
| `GET` | `/media/{id}/download` | optional | **bytes**, `Content-Disposition: attachment; filename=<original>` |
| `PUT` | `/media/{id}` (or `POST` with `_method=PUT`) | required | JSON; replaces the content, **keeps the id** |
| `PATCH` | `/media/{id}` (or `POST` with `_method=PATCH`) | required | JSON; sets or clears `entity_id`, files untouched |
| `DELETE` | `/media/{id}` | required | `{"success":true,"data":{"id":"…","deleted":true}}` |

**Listing** (`GET /media`): filters are all optional. `module` and `entity_id` follow the patterns in §3,
`media_type` is `image` or `file`, `year` is `2000..2100`, `month` is `1..12`, `page` ≥ 1, `per_page` is `1..200`
(default `50`). Items come back **newest first** (`created_at` desc, then id). Response:

```json
{"success": true, "data": [ …items… ], "meta": {"page": 1, "per_page": 50, "total": 3, "total_pages": 1}}
```

**Read rules** (`/media/{id}`, `/thumbnail`, `/metadata`, `/download`):

- With `X-Client-Code` the lookup is scoped to that tenant; another tenant's id is a `404`.
- Without the header only `public` media resolves; a `private` item answers `403`.
- Public media is sent with `Cache-Control: public, max-age=86400`, private media with `private, no-store`; every
  file response also carries `X-Content-Type-Options: nosniff` and `Last-Modified`. `view_url` and `thumbnail_url`
  of public media go straight into `<img>`.
- `visibility=private` exists but is only header-gated, not authorised; it is not used for product photos.

**Errors.** media-api's own errors use `{"success": false, "message": "...", "errors": {...}}` (`errors` is `{}` when
there is nothing field-specific):

| Status | When |
|---|---|
| `400` | header missing on a write/list route, or header not matching `^[a-z0-9-]{2,50}$` (`"Invalid client code."`) |
| `403` | private media requested without the owner's header |
| `404` | unknown or malformed id, other tenant's id, document thumbnail, file missing on disk |
| `422` | validation: bad file type or size, bad `module` / `entity_id` / `visibility`, bad list filters |
| `500` | storage failure (`"The media could not be stored."`) |

Unknown routes and wrong HTTP verbs are answered by Laravel itself as `{"message": "..."}` without the `success` key.

## 3. Upload contract

`POST /media`, `multipart/form-data`:

| Field | Required | Rule |
|---|---|---|
| `file` | yes | **Images**: JPEG, PNG, WebP (AVIF only when the server's GD can decode it; `/health` reports `avif`), max **10 MB**. Resized to fit **1600×1600** without upscaling, re-encoded as **WebP quality 80**, original discarded; a **400×400 WebP thumbnail** (quality 75) is always produced. **Documents**: PDF, TXT, CSV, DOC, DOCX, XLS, XLSX, max **25 MB**, extension kept. MIME is sniffed from the bytes, never from the browser; a `blocked_extensions` list rejects scripts, HTML, SVG, XML, archives and executables whatever the MIME says. |
| `module` | **yes** | `^[a-z0-9_-]{1,50}$`, e.g. `products`, `services`, `business` |
| `entity_id` | no | `^[A-Za-z0-9._-]{1,100}$`, your record's id as a string. If you also use the `media_attachments` table (§4 B) keep ids ≤ 64 chars, the width of its `entity_id` column. |
| `visibility` | no | `public` (default) or `private`. Leave it out; product photos are always public. |

```bash
curl -X POST -H "Accept: application/json" -H "X-Client-Code: lzhub" \
  -F "file=@product.png" -F "module=products" -F "entity_id=101" \
  https://media-api.mybizgate.com/api/v1/media
```

Response (`201`; `GET /media/{id}/metadata` returns the same object with `200`):

```json
{
  "success": true,
  "data": {
    "id": "01m639sgg2275fr73b2gb9s91r",
    "tenant": "lzhub",
    "module": "products",
    "entity_id": "101",
    "type": "image",
    "format": "webp",
    "mime_type": "image/webp",
    "visibility": "public",
    "original_filename": "product.png",
    "original_mime_type": "image/png",
    "size_bytes": 48213,
    "original_size_bytes": 203991,
    "width": 1600,
    "height": 1200,
    "thumbnail": true,
    "created_at": "2026-10-30T08:15:00+00:00",
    "updated_at": "2026-10-30T08:15:00+00:00",
    "view_url": "https://media-api.mybizgate.com/api/v1/media/01m639sgg2275fr73b2gb9s91r",
    "thumbnail_url": "https://media-api.mybizgate.com/api/v1/media/01m639sgg2275fr73b2gb9s91r/thumbnail",
    "metadata_url": "https://media-api.mybizgate.com/api/v1/media/01m639sgg2275fr73b2gb9s91r/metadata",
    "download_url": "https://media-api.mybizgate.com/api/v1/media/01m639sgg2275fr73b2gb9s91r/download"
  }
}
```

Documents have `type: "file"`, `format` = their extension (`pdf`, `docx`, …), `width`, `height` and `thumbnail_url`
are `null` and `thumbnail` is `false`. There is **no `status` field**: an item that exists is ready. The URLs are
deterministic (`{base}/media/{id}`, `/thumbnail`, `/metadata`, `/download`), so a consumer can rebuild them from the
id alone without calling media-api.

If the business record does not exist yet when the photo is uploaded, upload without `entity_id` and link it later:

```
PATCH /media/{id}        (X-Client-Code: lzhub, JSON or form body; entity_id must be present)
{"entity_id": "101"}     → 200 with the updated item; {"entity_id": ""} clears the link
```

## 4. Linking files to business records

### Option A — no table: use `module` + `entity_id` (simplest, use this first)

Upload with `module=products&entity_id=101` (or upload first and `PATCH` the `entity_id` once the product is
created). To show a product's images:

```
GET /media?module=products&entity_id=101&media_type=image   (X-Client-Code: lzhub)
```

Good enough for "all images of this record" on admin screens and cleanup jobs. Items come back newest first, so
there is no primary/gallery distinction and no custom ordering. Note the cost in §6: this listing reads the
`metadata.json` of every item under `products` for the tenant, so do not put it on a public page's hot path.

### Option B — small `media_attachments` table in the **consuming API** (when you need primary/gallery/ordering)

The consumer stores only the `media_id`; never paths, never bytes. One table per consuming API, scoped by tenant.
**media-api never reads or writes this table**; it does not know it exists.

```php
Schema::create('media_attachments', function (Blueprint $table) {
    $table->char('id', 26)->primary();       // ULID generated by the model (HasUlids)
    $table->string('tenant_id', 64);          // same value as X-Client-Code
    $table->string('entity_type', 48);        // product | service | business … (server-side allowlist)
    $table->string('entity_id', 64);          // business record id as string
    $table->char('media_id', 26);             // media-api ULID, no foreign key
    $table->string('role', 40)->default('attachment'); // primary | gallery | logo …
    $table->string('slot', 40)->nullable();   // = role for singleton roles, NULL for multi-file roles
    $table->unsignedInteger('sort_order')->default(0);
    $table->timestamps();

    $table->unique(['tenant_id', 'entity_type', 'entity_id', 'media_id', 'role'], 'ma_entity_media_role_unique');
    $table->unique(['tenant_id', 'entity_type', 'entity_id', 'slot'], 'ma_one_per_slot');
    $table->index(['tenant_id', 'entity_type', 'entity_id', 'role', 'sort_order'], 'ma_lookup');
    $table->index(['tenant_id', 'media_id'], 'ma_media_lookup');
});
```

`slot` gives "exactly one primary image" through the unique index while allowing many `NULL`-slot gallery rows.
Still send `module`/`entity_id` on upload so media-api's own listing stays useful.

Replacing a singleton (e.g. new primary image) is one local transaction: delete the old row for the slot, insert the
new one. Deleting a row only **detaches**; it does not call `DELETE /media/{id}`.

Production note: shared hosting has no SSH, and the FTPS deploy does not run `php artisan migrate`. Apply the
migration locally and, on production, through phpMyAdmin or another supported method, once.
`media-api/create_media_attachments.sql` is the same schema as a MySQL script for exactly that (run it in the
**consuming API's** database, never in media-api, which has none). Keep it in sync with the migration.

## 5. Server-side adapter and reference implementation (`client-api`)

`config/services.php`:

```php
'media_api' => [
    'base_url' => env('MEDIA_API_URL', 'https://media-api.mybizgate.com/api/v1'),
],
```

`app/Services/MediaApiClient.php` (as shipped in `client-api`; the only code there that talks to media-api):

```php
<?php

namespace App\Services;

use Illuminate\Http\Client\PendingRequest;
use Illuminate\Http\UploadedFile;
use Illuminate\Support\Facades\Http;
use Illuminate\Validation\ValidationException;

class MediaApiClient
{
    private function request(string $tenant): PendingRequest
    {
        return Http::acceptJson()
            ->withHeaders(['X-Client-Code' => $tenant])
            ->connectTimeout(10)
            ->timeout(60);
    }

    public function url(string $path): string
    {
        return rtrim((string) config('services.media_api.base_url'), '/').$path;
    }

    /** view/thumbnail/metadata/download URLs derived from the id: no round trip needed to list attachments. */
    public function urls(string $mediaId): array
    {
        return [
            'view_url' => $this->url("/media/{$mediaId}"),
            'thumbnail_url' => $this->url("/media/{$mediaId}/thumbnail"),
            'metadata_url' => $this->url("/media/{$mediaId}/metadata"),
            'download_url' => $this->url("/media/{$mediaId}/download"),
        ];
    }

    /** POST /media → the media-api `data` object of the new item. */
    public function upload(UploadedFile $file, string $tenant, string $module, ?string $entityId = null): array
    {
        $response = $this->request($tenant)
            ->attach('file', fopen($file->getRealPath(), 'rb'), $file->getClientOriginalName())
            ->post($this->url('/media'), array_filter([
                'module' => $module,
                'entity_id' => $entityId,
            ]));

        if ($response->status() === 422) {
            throw ValidationException::withMessages(
                $response->json('errors') ?: ['file' => [(string) $response->json('message')]]
            );
        }

        $response->throw();

        return $response->json('data');
    }

    /** GET /media/{id}/metadata. Fails unless the id exists and belongs to $tenant (media-api answers 404 otherwise). */
    public function metadata(string $mediaId, string $tenant): array
    {
        $response = $this->request($tenant)->get($this->url("/media/{$mediaId}/metadata"));

        if ($response->status() === 404 || $response->json('data.tenant') !== $tenant) {
            throw ValidationException::withMessages(['media_id' => ['Media not found for this tenant.']]);
        }

        $response->throw();

        return $response->json('data');
    }

    /** PATCH /media/{id}: link an already uploaded item to a record (null clears the link). */
    public function assign(string $mediaId, string $tenant, ?string $entityId): array
    {
        $response = $this->request($tenant)
            ->patch($this->url("/media/{$mediaId}"), ['entity_id' => $entityId ?? '']);

        if ($response->status() === 404) {
            throw ValidationException::withMessages(['media_id' => ['Media not found for this tenant.']]);
        }

        return $response->throw()->json('data');
    }

    /** DELETE /media/{id}. Only when no record in any consuming API references the id. */
    public function delete(string $mediaId, string $tenant): void
    {
        $this->request($tenant)->delete($this->url("/media/{$mediaId}"))->throw();
    }
}
```

Linking an id the frontend uploaded directly:

1. Derive the tenant server-side (`X-Client-Code` on the consuming API too, never from the request body).
2. Load the business record inside that tenant and authorise the user.
3. `$data = $mediaApi->metadata($mediaId, $tenant)`; check `data.type === 'image'` for photo roles.
4. If `data.entity_id` is empty or differs, call `$mediaApi->assign($mediaId, $tenant, (string) $record->getKey())`
   so media-api's own listing stays correct.
5. Insert/replace the attachment row (option B) or just record the id on the entity.
6. Return `view_url` / `thumbnail_url` (from the metadata, or rebuilt from the id); never paths.

Two upload patterns are both valid:

- **Browser → media-api → id → consuming API** (recommended; fewer bytes through client-api). For a new product the
  browser uploads without `entity_id`, the consuming API creates the product, then calls `assign()` with the new id.
- **Browser → consuming API → media-api** when the file and the record must be created together: upload first, then
  create the record and the link in one DB transaction; if the DB step fails, log the orphaned `media_id` for cleanup.

**CORS** on media-api (`config/cors.php`) allows `http://localhost:5173`, `http://127.0.0.1:5173`,
`https://lzhub.mybizgate.com`, any `https://<sub>.mybizgate.com`, plus the comma-separated `MEDIA_CORS_ORIGINS` env
list; headers `Accept`, `Content-Type`, `X-Client-Code`, `Authorization`, `X-Requested-With`; `Content-Disposition`
is exposed; no credentials.

**What `client-api` implements** (`app/Services/MediaApiClient.php`, `app/Services/AttachmentService.php`,
`config/attachments.php`, `app/Models/MediaAttachment.php`,
`database/migrations/2026_10_30_000000_create_media_attachments_table.php`, tests under `tests/Unit/Services` and
`tests/Feature/Http/Controllers/Api`). All endpoints require `X-Client-Code` and answer `{"data": …}`:

| Method | Path | Body | Effect |
|---|---|---|---|
| `GET` | `/api/v1/attachments/{entityType}/{entityId}?role=` | – | rows in role + sort order with media-api URLs (no call to media-api) |
| `POST` | `/api/v1/attachments/{entityType}/{entityId}` | `file` + `role` (multipart) | upload to media-api with `module`/`entity_id`, then store the row (`201`) |
| `POST` | `/api/v1/attachments/{entityType}/{entityId}` | `media_id` + `role` | verify `GET /metadata` (tenant, type), `PATCH` `entity_id` if it differs, store the row (`201`; `200` if already attached) |
| `DELETE` | `/api/v1/attachments/{attachmentId}` | – | detach only; media-api untouched |

`entityType` is `product`, `service` or `business` (mapped to modules `products`, `services`, `business`); roles are
`primary` and `logo` (one per record, images only), `gallery` (images) and `attachment` (any type).

## 6. Performance characteristics (why consumers keep their own table)

media-api has no index other than the directory tree, so costs grow differently from a database:

| media-api operation | What happens on disk | Grows with |
|---|---|---|
| serve `/media/{id}` with header | glob `tenants/{t}/{images,files}/*/*/*/{id}`, read one `metadata.json`, stream the file | number of module/year/month directories of the tenant |
| serve `/media/{id}` **without** header (every public `<img>`) | same glob across **all** tenants | tenants × directories |
| `GET /media?module=…&entity_id=…` | read and decode every `metadata.json` under the matching module/year/month, filter in PHP, sort, slice the page | every item in that module, whatever the page size |
| upload / replace / delete | build in a staging directory and `rename()` | constant |

Consequences for consumers:

- Build `view_url`/`thumbnail_url` from the id and let the browser and the LiteSpeed cache honour
  `Cache-Control: public, max-age=86400`. Do not call `/metadata` to display an image you already know the id of.
- Answer "which media belong to product 101" from your own `media_attachments` table (option B). Use the media-api
  listing for admin screens, reconciliation and orphan cleanup, narrowing it with `module`, `year` and `month`.
- media-api's repository is an interface (`MediaRepositoryInterface`), so a database-backed index can be added later
  without changing this contract.

## 7. Security notes

- All attachments are public product/service photos. `view_url` and `thumbnail_url` are safe to publish and cache.
- Caller authentication on media-api is intentionally not required. Anyone with a tenant code can upload, replace
  or delete that tenant's media, so keep upload/delete actions behind the consuming API's own user authorisation and
  add rate limits on any public form that triggers an upload.
- media-api validates MIME, size, extension and path segments; the consuming API validates business rules (which
  roles accept which types, per-tenant quotas).
- Never log or return storage paths. media-api never emits them; keep it that way on the consumer side.

## 8. Replace, detach, delete

- **Replace content, keep id**: `PUT /media/{id}` with a new `file` (and optional `visibility`). `module` and
  `entity_id` are kept, `updated_at` changes, and the new file is inspected again, so `type` can change (an image
  replaced by a PDF becomes `type: "file"` with no thumbnail). Links do not change; re-check `type` if a role is
  image-only.
- **Move to another record, keep id and file**: `PATCH /media/{id}` with the new `entity_id`.
- **Detach**: delete the attachment row only.
- **Delete file**: `DELETE /media/{id}` removes the whole media directory, and only when no record in any consuming
  API references the id. Nothing in media-api tracks usage, so the caller is responsible for that check.
- **Orphans**: `GET /media?module=…&entity_id=…` per tenant lets a cleanup job compare media-api against the
  consumer's rows; delete only after a retention period.

## 9. Checklist for a new consuming API

- [ ] Uploads send `file`, `module`, and `entity_id` (public visibility by default); uploads made before the record
      exists are linked afterwards with `PATCH /media/{id}`.
- [ ] Only `media_id` (26-char lowercase ULID) is stored; no paths, filenames or bytes in business tables.
- [ ] Linking an existing id goes through `GET /media/{id}/metadata` with the tenant header and checks `data.tenant`
      and `data.type`.
- [ ] Required attachments are committed in the same local DB transaction as the record; upload failures create no
      record; DB failures after upload are logged with the `media_id`.
- [ ] Detach never calls `DELETE /media/{id}`; physical deletion needs a global reference check.
- [ ] Listing pages build URLs from ids; the media-api list endpoint is not on a public hot path.
- [ ] Migration (option B) applied once per environment with `create_media_attachments.sql` where there is no SSH;
      FTPS deploy does not migrate.
- [ ] `php artisan test` passes in the consuming API with the media-api HTTP client faked (`Http::fake()`).
